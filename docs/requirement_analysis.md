# Auto Yon Koma 需求分析与优化建议

基于项目当前的设计思路以及 `prompts` 目录中已有的剧本家/分镜师设定，本项目的核心目标是：**将极简的用户输入（角色设定/简要剧情）通过大语言模型提取出结构化的四格漫画分镜，进而对接图像生成模型（如 Stable Diffusion/Midjourney 等）自动出图，最后完成图文排版，产出一张完整的四格漫画。**

为了满足“每一步都进行可视化，用户可以自由地选择继续、重新生成或修改”的需求，本应用应设计为一套**节点式/步骤式（Step-by-Step）的向导管道**。

---

## 1. 核心工作流设计 (Core Workflow)

整个系统将被拆分为四个主要的可交互阶段：

### 阶段一：构思与输入 (Ideation & Input)
- **用户操作**：输入故事主题（如：赛博朋克、校园日常）、角色设定（如：傲娇双马尾学妹），或用一两句话描述核心剧情点。
- **界面展示**：提供简单的表单，或者可选的“预设模板”（对应不同的 LLM 扮演角色，如 `资深动漫剧本家` 或 `连载四格漫画分镜导演`）。
- **交互边界**：用户确认输入后，请求后端或客户端本地的大模型 API。

### 阶段二：脚本与分镜生成 (Script & Storyboard)
- **系统行为**：调用 LLM（携带对应设定的 System Prompt），将用户的简案发散为具有“起、承、转、合”结构的四段分镜文本。
- **界面展示**：可视化呈现四个独立的“分镜卡片”。每个卡片上详细列出：景别、角色左右站位、动作神态、对话顺位及台词。
- **交互边界 (人工介入点)**：用户可以在这里**直接手动修改**某一个分镜的文本（例如把“大笑”改为“苦笑”），或者点击某个特定分镜卡片右上角的 **[重新生成此格]**，而非重跑整个剧本；确认无误后进入下一步。

### 阶段三：图像生成指令转换 (Prompt Engineering & Painting)
- **系统行为**：系统自动将上述分镜的描述翻译/提取为英文绘图 Prompt（包含正向和反向提示词）。如果选择了特定画风（如 `lovelive-3d-mmd-crispe`），自动挂载该画风预设的魔法词片段。
- **界面展示**：并行触发 4 次绘图 API 调用，画布上逐渐浮现四张画作（带 Loading 状态）。
- **交互边界 (人工介入点)**：用户如果发现第 3 格的构图完全跑偏，或者角色特征丢失，可单独选中第 3 格，**[微调图像 Prompt]** 后点击 **[重绘此格]**。这里还可以提供“锁定种子(Seed)”或“切换控制网(ControlNet/LoRA)”的高级选项。

### 阶段四：排版与嵌字渲染 (Typesetting & Rendering)
- **系统行为**：在生成的四张纯净底图上，系统根据前置分镜脚本中指定的“气泡形状”、“左右站位”、“对话顺位（上下位置）”以及“日语片假名拟声词（SFX）”，在画面图层上方通过 Canvas 算子或 OpenCV 叠加文字图层和气泡素材。
- **界面展示**：展示最终拼接好的垂直（1x4）或方阵（2x2）四格漫画全图。
- **交互边界 (人工介入点)**：提供一个轻量级的 2D 画布（如 Fabric.js），允许用户鼠标**拖拽对话气泡**的位置以避免遮挡人脸，或者双击修改错别字。最后点击 **[导出/保存]**。

## 2. 关键优化方向 (Key Optimizations)

根据当前仓库状态，如果要实现高自动化并保证质量，有以下几个急需优化的技术点：

### 2.1 LLM 输出结构化优化 (JSON 优先)
当前目录下的 `lovelive 漫画分镜师.md` 提示词非常优秀，它严格规定了排版顺位和空间控制，但其输出格式是 Markdown 文本。
为了让后端程序能稳定地把分镜数据拆解并传给绘图与排版模块，强烈建议优化 Prompt 的 `OutputFormat`，要求 LLM **输出严格的 JSON 格式**（或者 XML）。这样能避免复杂的正则匹配导致解析失败。

*JSON 设计示例：*
```json
{
  "panel_1": {
    "title": "起：相遇",
    "camera": "中景/平视",
    "background": "教室，阳光明媚",
    "characters": [
      { "name": "角色A", "position": "left", "action": "微笑招手", "dialogue": "早上好！", "bubble": "爆炸框", "order": 1 }
    ],
    "sfx": ["キラキラ"]
  }
}
```

### 2.2 角色特征一致性保障 (Character Consistency)
漫画最致命的问题是四格内人物长得完全不一样。必须在架构设计之初考虑此问题：
- **方案 A (最稳)**：让用户在应用内预先登记“角色库”，绑定已注册好的 LoRA 模型或固定的英文外貌 Prompt 描述簇。自动生成的画图 Prompt 会强制拼接这些特征标签。
- **方案 B (灵活)**：在管道的绘图阶段，支持垫图（ControlNet Reference Only 或 IP-Adapter），保证基于同一张参考图生成四个不同动作的面板。

### 2.3 前后端分离与高并发推流 (Architecture)
由于 AI 生成是典型的耗时任务，建议分离前端与后端：
- **前端 WebUI**：建议使用 React / Vue 构建步骤条表单面板和气泡拖拽画布。
- **后端服务**：可使用 Node.js / Python 搭建，并通过 **WebSocket / Server-Sent Events (SSE)** 将 LLM 逐字输出的剧本流，以及 SD 出图的进度条（进度百分比）推送到前端，提升用户等待体验。

### 2.4 中间态数据持久化 (Caching & State Management)
工作流包含四步，如果用户在第三步（出图）刷了十遍没满意的图，他决不希望退回第二步修改错别字时，导致所有图片丢失变回草稿状态。
- **建议**：设计树状/分支的历史记录机制，即每次重新生成一格，在内存/本地存储（LocalStorage/IndexedDB）中就多出一个子节点。用户可以在多次生成的版本中自由切换对比。

## 3. 建议的初步技术栈 (Recommended Tech Stack)

- **前端界面**：React/Next.js (或 Vue3)
- **状态管理**：Zustand / Redux (用于管理庞大的逐步状态和分镜枝干数据)
- **图文排版交互**：Fabric.js 或 Konva.js (支持气泡拖拽、文字绑定出图)
- **后端接口**：FastAPI (Python，方便对接机器学习相关生态) 
- **AI 对接**：
  - OpenAI API / Anthropic API / Ollama (用于剧本分镜)
  - Stable Diffusion WebUI API / ComfyUI API / NovelAI (用于批量出图)
